# UDP 远程终端

基于 UDP 协议实现的可靠远程终端程序。项目按实验指导书要求完成基础远程命令执行能力，并在此基础上追加实时输出、输出方向回退 N 步 ARQ 可靠传输、控制字符增强、接收端流量控制、终端窗口大小同步和 PTY/ConPTY 全屏交互等功能。

## 一、基础功能部分

### 1.1 已实现功能与实现方法

| 基础功能 | 实现方法 |
|---|---|
| UDP 基础通信 | 客户端可指定服务端 IP 和端口；服务端绑定 UDP 端口并循环接收报文。 |
| 自定义协议封包/解包 | 统一使用固定 13 字节头部，包含魔数、报文类型、序列号、数据长度、客户端 ID；非法魔数、非法类型、长度不匹配报文会被直接丢弃。 |
| 基础可靠传输 | 使用 ACK、超时重传、序列号去重和保序机制补齐 UDP 不可靠问题；当前命令输入方向仍使用停等 ARQ。 |
| 基础命令执行 | 服务端按客户端提交的命令启动子进程执行，捕获 stdout/stderr 后通过 UDP 返回客户端；Windows 下按字符串交给系统 shell 执行，兼容 `python -c "..."` 这类带双引号的命令，Linux/macOS 下使用 `bash -c` 执行。 |
| 持久 `cd` | `cd` 由服务端内置处理，不启动外部子进程；每个客户端维护独立 `cwd`，后续命令会在该目录下执行。 |
| 基础控制字符处理 | 命令输入会规范化 `\n`、`\r`、退格 `\b`、Delete `\x7f`，避免用户输入中的基础控制字符破坏命令内容。 |
| 多客户端支持 | 服务端按客户端 ID 维护独立会话状态，包括地址、心跳时间、收发序列号、当前工作目录、接收窗口、终端大小和当前执行进程。 |
| 心跳检测 | 客户端每 5 秒发送心跳；服务端收到心跳后回复 ACK；启动连接阶段约 2 秒未收到 ACK 会判定连接失败；连接成功后连续 3 次心跳未收到 ACK 才提示连接异常并退出，心跳失败后会约 2 秒快速重试；服务端约 30 秒无心跳则清理离线客户端。 |
| SSH 风格提示符 | 心跳 ACK 携带服务端用户名、主机名、当前目录和服务端本次启动的会话 ID；客户端显示 `[user@host dir]$` 或 `[user@host dir]#` 格式提示符，并用会话 ID 识别服务端重启。 |
| 基本异常处理 | 命令不存在、服务端不可达、网络超时、非法报文等场景不会导致程序崩溃；长时间运行命令期间如果短暂断网后同一服务端会话恢复，客户端会继续等待并接收服务端重传输出；如果服务端重启导致当前命令输出不可恢复，客户端会解除当前命令等待并回到提示符；如果连续心跳失败达到断线阈值，会唤醒命令输出等待和发送等待并退出客户端，并在退出前收尾接收/心跳线程。 |

### 1.2 基础阶段支持的命令

基础阶段适合执行**非交互式、能在有限时间内结束**的命令。

| 操作系统 | 常用命令示例 |
|---|---|
| Windows | `dir`、`cd`、`ipconfig`、`echo`、`tasklist`、`netstat`、`type` |
| Linux/macOS | `ls`、`pwd`、`ip addr`、`ifconfig`、`echo`、`ps`、`netstat`、`cat`、`df` |

说明：

- `cd` 是服务端内置命令，会更新当前客户端自己的远端工作目录，不影响其他客户端。
- 客户端中输入 `exit` 用于退出客户端，不会发送到服务端执行。
- 普通命令不再设置固定执行时长上限；会运行到自然退出、用户按 Ctrl+C 中断、客户端离线清理或服务端停止。
- 普通命令路径不分配 PTY，适合非交互式命令；需要全屏或交互输入时使用拔高阶段的 PTY 命令。

## 二、进阶功能部分

### 2.1 已实现功能与实现方法

| 进阶功能 | 实现方法 |
|---|---|
| 远程 Ctrl+C 中断 | 客户端在命令执行期间捕获 Ctrl+C，普通命令路径发送中断报文并由服务端中断对应进程组；PTY 路径会把 Ctrl+C 作为 `\x03` 写入远端伪终端。提示符处 Ctrl+C 不退出客户端。Windows 普通命令路径会合并 stdout/stderr 以保持中断输出顺序，把系统控制事件提示统一显示为更接近本地终端的 `Control-C`，并在 `ping` 等持续输出命令出现中断提示后停止转发尾部残余回复。 |
| Tab 处理 | 普通命令路径中 Tab 会作为命令字符传递给远端 shell，不在客户端改写为空格；PTY 模式下 Tab 作为原始按键传给远端伪终端。 |
| ANSI 转义序列过滤 | 普通命令路径输入侧会过滤 ANSI 转义序列，避免粘贴控制序列污染命令；普通输出显示前也会过滤 ANSI 转义序列，避免颜色、光标移动等控制序列造成乱码或界面错乱。PTY 模式下输出不做过滤，以保证全屏程序正常刷新。 |
| 输出方向回退 N 步 ARQ | 客户端到服务端的命令输入继续使用停等 ARQ；服务端到客户端的命令输出使用固定上限的小窗口批量发送，客户端只接收期望序号分片、丢弃乱序分片并返回累计 ACK；服务端收到累计 ACK 后整体滑动窗口，最早未确认分片超时时从该分片开始重传当前发送窗口。只要客户端会话未被心跳清理，输出分片会持续重传并使用客户端最新地址发送，短暂断网恢复后可继续确认并显示。 |
| 实时命令输出 | 服务端不再等待命令结束后一次性返回输出，而是持续读取子进程 stdout/stderr，读到内容后立即可靠发送给客户端。 |
| 输出编码兼容 | 服务端普通命令路径优先按 UTF-8 解码命令输出；如果检测到非法 UTF-8，再回退到服务端本机编码（Windows 常见 GBK/CP936），最后统一转成 UTF-8 发给客户端，兼容 Windows 普通命令和 UTF-8 文件内容。 |

补充说明：指导书中的“回退 N 步 ARQ”在本项目中用于服务端到客户端的输出方向。发送端维护 `base` 和 `next_to_send`；接收端不缓存乱序分片，只按序显示并用 ACK 序号表示已经连续收到的最后一个分片；发送端超时后回退到 `base`，重传当前窗口内尚未累计确认的分片。

### 2.2 进阶阶段支持的命令

在基础命令范围上，当前进阶实现额外适合以下场景：

| 场景 | 示例 |
|---|---|
| 持续输出且会刷新 stdout/stderr 的命令 | Windows: `ping -n 5 127.0.0.1`；Linux/macOS: `ping 127.0.0.1` |
| 大批量输出命令 | Windows: `for /L %i in (1,1,1000) do @echo XXXXXXXXXX`；Linux/macOS: `seq 1 1000` |
| 查看文本文件 | Windows: `type README.md`；Linux/macOS: `cat README.md` |
| 输出 ANSI 颜色文本 | Windows/Linux 均可使用 `python -c "print('\033[31mRED_TEXT\033[0m')"`，普通命令路径会显示过滤后的普通文本。 |

限制说明：

- 实时输出传输的是子进程已经写出并 flush 到 stdout/stderr 的内容；部分程序检测到 stdout/stderr 是管道时会自行缓冲，可能仍然延迟显示。
- 普通命令路径不分配真实终端，因此不适合 `vim`、`top`、交互式 Python、`sudo` 提示输入等需要完整交互终端的程序；这些命令应使用拔高阶段的 PTY 路径。

## 三、拔高功能部分

### 3.1 已实现功能与实现方法

| 拔高功能 | 实现方法 |
|---|---|
| 滑动窗口流量控制 | 客户端在累计 ACK 中携带可接收分片数和字节数窗口通告；服务端发送窗口取固定输出窗口和客户端通告分片数的较小值，只在有效窗口允许时发送新的输出分片，避免持续压入超出客户端处理能力的数据。 |
| 终端窗口大小同步（WINCH） | 客户端连接成功、进入 PTY 命令前以及窗口大小变化时发送行列数；服务端按客户端 ID 保存 `rows/cols`，并在 PTY/ConPTY 会话存在时立即设置伪终端大小。 |
| 普通命令无固定时长上限 | 普通命令路径移除基础阶段的 30 秒硬超时，长时间运行命令会持续转发实时输出，直到命令自然结束、用户 Ctrl+C 中断、客户端离线触发清理或服务端停止。 |
| PTY/ConPTY 全屏交互 | 服务端普通命令路径保持不变；`pty <command>` 以及 `top`、`vim`、`vi`、`nano`、`less` 会进入 PTY 路径。POSIX 客户端进入 raw 输入模式发送原始按键字节；Windows 客户端使用 Console API 读取键盘事件，再将字符或特殊键转换为 `TYPE_STDIN` 发送；服务端写入对应客户端的 PTY，PTY 输出原样通过可靠输出链路返回客户端。 |
| 全屏界面原样渲染 | PTY 模式输出不解码、不过滤 ANSI 转义序列，客户端直接写入本地 stdout buffer，因此光标移动、清屏、备用屏幕、界面刷新等控制序列可以正常工作。 |
| Windows ConPTY 支持 | Windows 10/11 服务端通过可选依赖 `pywinpty` 使用原生 ConPTY；未安装时，非 PTY 普通命令不受影响，显式或自动 PTY 命令会返回明确错误提示。Windows PTY 输入使用 `ReadConsoleInputW` 读取 KeyDown 事件，跳过 IME 产生的空字符事件，将普通字符编码为 UTF-8、退格映射为 DEL、方向键等特殊键映射为 ANSI 序列，并通过 UTF-8 增量解码写入 ConPTY，改善 `vim` 中文输入和编辑延迟。 |
| PTY 清理与隔离 | 每个客户端维护独立 PTY 会话、窗口大小、接收窗口和进程状态；心跳超时或客户端离线时，服务端会清理该客户端的 PTY/ConPTY 会话和当前进程。 |

补充说明：客户端窗口通告同时包含可接收分片数和可接收字节数；服务端会保存两者，其中实际发送节奏以固定输出窗口和客户端通告分片数的较小值作为有效窗口，字节数用于反映接收端可用容量。

### 3.2 拔高阶段支持的命令

| 场景 | 示例 | 退出方式 |
|---|---|---|
| 显式 PTY 命令 | `pty bash`、`pty sh`、`pty cmd`、`pty powershell` | 输入 `exit` |
| 全屏监控程序 | `top` 或 `pty top` | 按 `q` |
| 全屏编辑器 | `vim README.md` 或 `pty vim README.md` | 输入 `:q!` 或正常保存退出 |
| 分页/全屏查看 | `less README.md` 或 `pty less README.md` | 按 `q` |

平台说明：

- Linux/macOS/WSL 服务端使用 Python 标准库 PTY，无需额外依赖即可支持 `top`、`vim` 等程序。
- Windows 10/11 原生服务端通过可选依赖 `pywinpty` 支持 ConPTY，安装方式见“4.1 依赖安装”。
- POSIX 非 TTY 环境无法进入完整 raw 输入模式；Windows 客户端需要在真实控制台环境中读取完整键盘事件。建议在真实终端中手动验证 `top`、`vim`、窗口缩放等交互行为。
- PTY stdin 为低延迟交互路径，客户端会按序号发送输入分片，服务端 ACK 并按序写入 PTY；客户端当前不等待 stdin ACK 重传，因此该方向不同于普通命令停等 ARQ 和输出 Go-Back-N 可靠传输。
- `pty bash` / `pty sh` 内部执行的 `cd` 只影响该交互 shell；退出后客户端提示符仍以服务端维护的普通命令 `cwd` 为准。需要持久切换目录时，仍建议在普通提示符下执行 `cd`。

## 四、使用方法

### 4.1 依赖安装

基础命令、进阶可靠传输和 Linux/macOS/WSL 的 PTY 功能只依赖 Python 3 标准库。Windows 10/11 原生服务端如果需要使用 `pty cmd`、`pty powershell`、`vim`、`less` 等 PTY/ConPTY 命令，需要安装可选依赖：

```bash
pip install pywinpty
```

未安装 `pywinpty` 时，普通命令仍可正常使用；显式或自动 PTY 命令会返回缺少依赖的明确提示。全屏程序还需要服务端系统已安装对应命令本身，例如 `vim`、`top` 或 `less`。

### 4.2 启动服务端

```bash
python server.py [端口]
```

默认监听 `0.0.0.0:9999`。例如：

```bash
python server.py 10000
```

也可以指定监听地址：

```bash
python server.py 10000 --host 0.0.0.0
```

### 4.3 启动客户端

```bash
python client.py [服务端IP] [服务端端口]
```

默认连接 `127.0.0.1:9999`。例如：

```bash
python client.py 192.168.1.100 10000
```

客户端启动后会先发送心跳并等待服务端 ACK；如果约 2 秒内没有收到回复，会打印连接失败并直接退出。连接成功后才会显示类似 `[user@host dir]$` 的提示符；之后客户端每 5 秒发送一次心跳，单次等待约 2 秒，连续 3 次未收到 ACK 才会提示连接异常并退出。若某次心跳失败，下一次会约 2 秒后快速重试；如果短暂断网后心跳恢复且服务端会话 ID 未变化，客户端不会中断当前普通长命令，而是继续等待服务端重传输出和命令结束标记。若心跳恢复但服务端会话 ID 已变化，说明服务端进程已重启、原命令及其输出状态不可恢复，客户端会提示当前命令输出不可用并返回提示符。若连续失败达到断线条件，即使正在执行 `ping` 这类长时间运行命令，断线判定也会唤醒当前命令等待并退出客户端。服务端会继续向客户端最新地址重传 Go-Back-N 窗口内未累计确认的输出分片，网络恢复后客户端可继续 ACK 并显示后续输出。

每次普通命令或 PTY 命令输出结束后，服务端会发送一个携带当前工作目录的结束标记，客户端收到后自动更新提示符并显示下一条提示符，不需要额外再按一次回车。

客户端中输入 `exit` 可以退出。普通命令执行期间按 Ctrl+C 会发送远程中断报文；PTY 模式下 Ctrl+C 会作为 `\x03` 写入远端伪终端，更接近真实本地终端行为。Linux/macOS TTY 通常由终端回显 `^C`，客户端只补换行；Windows 或非 TTY 环境由客户端打印 `^C`。

## 六、协议格式

固定头部 13 字节，采用大端字节序，发送端将单个 UDP 报文总长度控制在 1472 字节以内以避免 IP 分片。

| 字段 | 长度 | 说明 |
|---|---:|---|
| 魔数 | 2B | 固定 `0x5554`，用于识别合法报文 |
| 报文类型 | 1B | `0x01` 命令输入，`0x02` 命令输出，`0x03` ACK，`0x04` 心跳，`0x05` 中断，`0x06` PTY stdin，`0x07` 终端大小同步，`0x08` 接收窗口通告 |
| 序列号 | 4B | 用于 ACK、去重、保序和重传 |
| 数据长度 | 2B | 数据段长度 |
| 客户端 ID | 4B | 区分多个客户端 |
| 数据段 | 可变 | 命令内容、输出内容、终端输入字节或控制元信息 |

当前实现中，普通命令和输出序列号使用 `0..0xFFFFFFFE` 循环递增，`0xFFFFFFFF` 保留给心跳报文使用。中断报文用于通知服务端中断当前命令，不参与命令序列去重。

控制 payload：

- `ACK` 可携带接收窗口通告；输出方向 ACK 使用累计确认语义，序列号表示客户端已经按序收到的最后一个输出分片，payload 中的窗口通告表示后续可接收容量；该通告编码为 `b'\x00WIN:' + struct.pack('>H I', available_packets, available_bytes)`。
- `TYPE_WINDOW_UPDATE` 可在没有新输出 ACK 时单独通告接收窗口变化，payload 编码同 ACK 中的接收窗口通告。
- `TYPE_RESIZE` 携带终端行列数，用于设置远端 PTY/ConPTY 大小；payload 编码为 `b'\x00SZ:' + struct.pack('>H H', rows, cols)`，行列范围均为 `1..1000`。
- `TYPE_STDIN` 携带 PTY 模式下的终端输入字节；该方向服务端会回 ACK 并按序写入 PTY，但客户端不做停等重传，以优先保证交互延迟。
- 输出结束标记作为 `TYPE_OUTPUT` 分片发送，payload 编码为 `b'\x00CWD:' + cwd.encode('utf-8')`，客户端据此更新下一次提示符目录并结束当前命令输出等待。
- 心跳 ACK 可携带提示符信息，payload 编码为 `b'\x00PROMPT:' + '\0'.join((user, host, cwd, server_session_id)).encode('utf-8')`，客户端据此更新用户名、主机名和当前目录；`server_session_id` 是服务端本次启动生成的随机标识，用于区分短暂断网恢复和服务端重启后的新会话。

```bash
python test_all.py
```
